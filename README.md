## What this repository is

This repository owns the working public application and the shared operational meaning of an identified job.

A project is defined in System. The Store answers what its own declared stock, capability, modeled work, and economics can provide. System keeps the definition, the exact Store answer, the customer's next decision, and the consequential record together without turning a Store answer into project meaning or machine authority.

For the current publication source, inspected Store revision, simulation boundary, and historical pointers, start with [`SYSTEM-MASTER.md`](SYSTEM-MASTER.md#13-application-architecture-and-deployment).

## Five bounded demonstrations

The current public library presents five demonstrations in the order defined by the shared trail contract:

| Project | What it exercises |
| --- | --- |
| **Start your own** | One user-defined board job: cuts and a bounded spot operation. |
| **Critical fit** | An alcove/shelf insert whose definition is driven by an exact opening. |
| **Space utilization** | A larger window-seat assembly using the same Store boundary. |
| **Outdoor build** | A project entered from a published picnic-table plan. |
| **Playhouse arched window** | Sheet goods and the S-001 Store path instead of a dimensional-board path. |

These are different project classes, not five copies of one configurator. Their shared journey is the protocol; their project facts remain their own.

The [registered component tool](https://system-candidate-production.up.railway.app/live/component-tool.html?v=public-conformance-20261017) supports separate component work through the same definition and Store boundary.

## One trail

Every project uses the same six labels, in the same order:

**Intent → The bench → The Store answers → Your call → We cut it → Pick up & build**

Before the steps sits **Idea**, an unnumbered workspace for what you want and the source information you bring—photos, scans, sketches, descriptions, or prior work; it is not a step, and nothing on it becomes a controlling fact by itself. Intent (step 1) sets this job's scope and carries forward what you already supplied, so nothing known is asked again. The words are defined in [`docs/DEFINITIONS.md`](docs/DEFINITIONS.md).

The machine-readable contract is [`public/live/stb-trail-contract.js`](public/live/stb-trail-contract.js). It names all five project tiles. There are no operational trail-rule exemptions. Two declared presentation exceptions preserve that protocol: Window Seat may offer **Intent | One full scroll** on its Idea line; Start your own opens on **Intent**, with its unnumbered Idea intake one back control away.

The labels are deliberately broader than page count. A project may need several pages inside one step, but it does not get a different authority sequence.

## How the definition reaches the command

The confirmed project-definition revision is the controlling description of the component to be made. System preserves that meaning and asks Store what it can provide. Store contributes its identified material, capability, modeled work, and economics; local machine engineering contributes registered datums, tooling, transforms, and execution rules. Those manufacturing facts may resolve how to make the defined result; they may not silently redefine it.

The [Project 1 current digital manufacturing proof](https://github.com/GeorgePlattDemo/store-zero/blob/main/docs/project-1-digital-trail/README.md) demonstrates this information path with current bounded SPF specimens: the customer's definition and independent manifest lead to a fresh Store answer, customer acceptance, an exact accepted packet, registered lowering, and virtual replay without a second design entry. The maintained proof is regenerated from operative inputs. The original sealed Project 1 publication is separate historical evidence, not current acceptance or commissioned execution evidence.

For a commissioned implementation, after the required releases, selected material would be loaded and registered to the machine's established references. The definition's dimensions, feature locations, and required operations would be transformed into local coordinates and ordered commands. Inspection would then determine conformance against that same revision. The current demonstration establishes no such physical run.

**The definition controls the required result. Local release permits execution. Inspection establishes conformance.**

## The Store boundary

System does not own Store facts or calculate a substitute Store answer.

The application consumes one inspected Store revision through `STORE_CANDIDATE.inspectedCommit` in [`src/system/store-candidate.ts`](src/system/store-candidate.ts). The Store evaluates the identified request and returns its own result. A different System page or project wrapper may not recreate that result locally because doing so would collapse the boundary this repository is meant to demonstrate.

A Store `SUPPORTABLE` answer is not fabrication authorization. A changed definition requires a fresh Store evaluation for the changed version.

## What the evidence register establishes

The [testing and verification record](SYSTEM-MASTER.md#14-testing-and-verification) and [manufacturing conformance register](SYSTEM-MASTER.md#155-manufacturing-contract-conformance-register) connect current claims, evidence, and open obligations to identified revisions. Historical and candidate results remain tied to the exact identities they actually proved.

Among the properties already recorded there are Store-backed dimensional and sheet software paths, durable custody of Store requests and answers, rejection of stale historical requests as current requests, quarantine of malformed or authority-bearing answers, preservation of Store refusal, and explicit non-claims for physical production and physical execution authority.

Required [five-project Chromium acceptance](scripts/browser-five-jobs.mjs) and the maintained [Project 1 current digital proof](https://github.com/GeorgePlattDemo/store-zero/blob/main/docs/project-1-digital-trail/README.md) exercise identified parts of the published journey, Store integration, acceptance, and modeled execution. Only those exact checks and revisions establish their stated claims—not older acceptance evidence or a green workflow alone.

## What is simulated or modeled

The current application is a software demonstration, not a commissioned production system.

- Store Zero is a modeled reference lumberyard with declared catalog, represented stock, capability, economics, and evaluation clocks. Its bounded answers are evaluated by Store software.
- Store prices are budgetary reference estimates, not binding quotations.
- Machine time is modeled from declared indexing, tool motion, feeds, passes, and handling. Current Project 1 evidence includes generated virtual commands and replay; the original historical controller-oriented source remains uncompiled, and neither supplies measured commissioned production time.
- Offer, acceptance, payment, yard queue, allocation/release narrative, cutting, staging, and handoff are simulated where shown in the demonstration.
- No commissioned D-001 or S-001 physical production is established.
- The software does not issue physical execution authority.

The Store owns the current registered modeled machine and capability declarations: [Scan-to-Build Store](https://github.com/GeorgePlattDemo/store-zero).

## Limits
